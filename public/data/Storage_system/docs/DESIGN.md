# Storage System Design

## Purpose

The storage system is designed for local, future-proof storage of company-analysis outputs. The immediate inputs are JSON files in the current directory, but the database is intentionally broader than those files.

It supports future analyses of:

- Different companies.
- Different scoring frameworks.
- Different content types.
- Different source types.
- Different analysis dates.
- Different schema versions.

The main design choice is to make `analysis_runs` the central unit of storage.

## Why Analysis Runs Are Central

A company is not the same thing as an analysis.

For example, Snowflake may be analyzed in May 2026 using version `1.1.0` of the technology-innovation framework. It may be analyzed again later with a new scoring formula, new sources, a different analyst request, or a different scope.

Those should be separate records.

Therefore:

- `companies` stores durable company identity.
- `analysis_runs` stores a specific dated analysis of a company.
- `analysis_frameworks` stores the methodology used by that run.
- `analysis_outputs` stores derived scores.
- `sources`, `evidence_items`, `analysis_layers`, and `analysis_metrics` store the auditable basis for the result.

## Hybrid Relational And JSON Model

SQLite does not have a native JSON type like Postgres `jsonb`, but SQLite supports JSON validation and JSON functions when JSON1 is available. This system uses `TEXT` columns with `CHECK (json_valid(...))` constraints for JSON fields.

The system stores data in two ways:

1. Full raw JSON is preserved in `analysis_runs.raw_payload_json` and `analysis_runs.raw_scored_json`.
2. Important queryable fields are normalized into relational tables.

This hybrid model is intentionally conservative:

- Raw JSON protects against future schema changes.
- Relational tables support dashboards, filtering, joins, and analytics.
- JSON columns hold flexible metadata without requiring a migration for every new field.

## Table Responsibilities

### `companies`

Stores stable company identity.

Important fields:

- `legal_name`
- `display_name`
- `slug`
- optional country, sector, industry
- `metadata_json`

Do not use ticker as the primary company identity. Tickers can change, companies can delist, companies can have multiple exchanges, and private companies may not have tickers.

### `company_identifiers`

Stores tickers, CIKs, ISINs, LEIs, or future identifiers.

The current importer extracts:

- ticker strings such as `NYSE: SNOW`
- CIK values from richer v2 `research_context.company_identifiers`

Future importers can add:

- ISIN
- LEI
- FIGI
- PermID
- internal CRM IDs
- subsidiary IDs

### `analysis_frameworks`

Stores the methodology and scoring system.

Current fields include:

- skill name
- skill version
- schema version
- scorer name
- scorer version
- metric rules version
- full framework metadata JSON

This allows scores generated by different framework versions to coexist.

### `analysis_runs`

Stores one imported analysis.

Important fields:

- `run_uid`
- `company_id`
- `framework_id`
- `mode`
- `research_date`
- `analyst`
- `user_request`
- `time_horizon`
- `research_mode`
- `benchmark_ready`
- `focus_technologies_json`
- `research_context_json`
- `normalization_notes_json`
- `storage_metadata_json`
- `raw_payload_json`
- `raw_scored_json`
- hashes for payload, scored output, and combined import

The importer is idempotent by `run_uid`. Re-importing the same run replaces the old normalized copy of that run.

### `sources`

Stores source documents independently from a specific run when possible.

The current files use local source IDs such as `src_001`. Those IDs are not globally meaningful. The database therefore deduplicates sources using a hash based on URL when available, otherwise title, publisher, document date, and type.

### `run_source_refs`

Maps a local source ID from an analysis run to the deduplicated global `sources` table.

This preserves local IDs such as `src_001` while avoiding global source duplication.

### `evidence_items`

Stores factual evidence extracted during research.

Important fields:

- local evidence ID, such as `ev_001`
- source link
- layer
- metric codes
- fact type
- fact text
- quote or excerpt when available
- raw value and unit
- period start and end
- whether it is company-attributable
- whether it is a field proxy
- verification status
- limitations
- raw evidence JSON

Evidence is first-class because scores must remain auditable.

### `analysis_layers`

Stores layer-level summaries and scores.

The current framework uses five layers:

- Science
- IP
- Industrialization
- Adoption
- Policy & Economics

The schema does not hardcode these layers. Future frameworks can use different layer labels and ordering.

### `analysis_metrics`

Stores metric-level values, weights, units, verification status, and normalization metadata.

Every metric keeps:

- normalized relational fields
- full raw metric JSON
- full normalization JSON

This allows future scoring formulas to become more complex without breaking old records.

### `metric_evidence_links`

Stores many-to-many links between metrics and evidence.

This matters because:

- one metric can be supported by many evidence items
- one evidence item can support multiple metrics
- future systems may add contradiction or context relationships

### `analysis_outputs`

Stores final derived scores and verdicts.

This table is intentionally separate from `analysis_runs` because scores are derived outputs. The raw payload can exist without a scored output.

### `content_artifacts`

Stores future generated content.

Examples:

- dashboard JSON
- rendered HTML
- report metadata
- slide deck references
- Instagram carousel data
- PDF file paths
- theme information

This table is what allows the storage system to expand beyond innovation scoring.

### `raw_documents`

Stores ingested source documents that may be used across future runs.

Examples:

- annual reports
- 10-K filings
- earnings-call transcripts
- patent exports
- PDFs
- scraped web pages
- technical papers

The current importer does not populate this table yet. It is included to make the system ready for document ingestion.

### `audit_events`

Stores import events and future operational history.

## Views

### `v_run_summary`

Summarizes each analysis run with:

- company
- ticker
- date
- framework
- score
- verdict
- layer count
- metric count
- evidence count
- source count

This is the first view to use for dashboard lists.

### `v_metric_evidence`

Joins metrics to supporting evidence and sources.

This is useful for explainability and audit views.

## Import Behavior

The importer looks for:

```text
*_payload.json
```

For each payload file, it looks for a matching:

```text
*_scored.json
```

The base filename becomes the fallback run UID for legacy files. Rich v2 files use `research_run.run_id`.

Current examples:

```text
snowflake_inc_payload.json -> snowflake-innovation-2026-05-04
uber_technologies_inc_payload.json -> uber-innovation-2026-05-04
postnl_nv_payload.json -> postnl_nv
```

## Why Raw JSON Is Preserved

Raw JSON is preserved for four reasons:

1. Auditability: the exact source artifact remains available.
2. Compatibility: old records survive future schema changes.
3. Reprocessing: future importers can re-normalize old data.
4. Export: users can reconstruct the original payload/scored pair.

## Future-Proofing Rules

When extending this system:

1. Add new columns only for fields that are frequently queried.
2. Put rare or evolving fields in JSON metadata columns.
3. Preserve raw source artifacts.
4. Version every framework and scorer.
5. Do not overwrite historical analysis runs unless intentionally re-importing the same `run_uid`.
6. Keep source IDs local to runs and use global source deduplication separately.
7. Store generated content in `content_artifacts`, not in analysis tables.

## Suggested Next Extensions

Useful next additions would be:

- A `documents ingest` command for PDFs, filings, transcripts, and scraped pages.
- A `content-artifact create` command for dashboards, reports, and carousel assets.
- A lightweight read-only web dashboard.
- A migration system beyond the initial `schema_migrations` table.
- Full-text search over evidence facts and extracted documents.
- Export commands for CSV, JSONL, and dashboard-ready JSON.
